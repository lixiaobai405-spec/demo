## 一、核心评估维度设计

### 1.1 设计原则：简单且科学的张力平衡

> **核心设计挑战**：用户填表意愿与评分科学性之间存在天然张力——维度越多越精准，但用户越不愿意填；维度越少越简单，但推荐结果缺乏说服力。

本方案采用**"三维评估模型"**，三个维度分别对应 AI 项目落地的三大决定性要素：

```
痛点迫切度（Pain）× 数据基础度（Data）× 实施可行度（Feasibility）
```

**为什么是这三个维度，而不是其他？**

| 维度 | 选择理由 | 不选的替代维度 | 排除原因 |
|------|--------|------------|--------|
| **痛点迫切度** | AI 项目若不解决真实痛点，即使技术先进也无商业价值；痛点是优先级的"分子" | 战略重要性 | 与痛点高度重叠，且用户难以客观判断 |
| **数据基础度** | AI 落地的核心壁垒是数据，而非算法；无数据的 AI 是空中楼阁；数据是"燃料" | 技术成熟度 | 通用 AI 技术已足够成熟，真正的变量是数据 |
| **实施可行度** | 决定"能不能快速出结果"，直接影响组织信心与 ROI 时间窗；是落地的"阻力系数" | 投资回报率 | ROI 是结果变量，无法独立评估；其他三维已覆盖其决定因素 |

### 1.2 三维模型的底层逻辑对应关系

```
AI 商业创新底层公式：

优先级 = f（为什么要做 × 能不能做 × 好不好做）
          ↕              ↕            ↕
       痛点迫切度    数据基础度    实施可行度
       （Pain）      （Data）    （Feasibility）
       "需求侧拉力"  "技术侧支撑"  "执行侧阻力"
```

**三维的互补逻辑：**

- **仅痛点高，无数据基础** → 方向对，但 AI 无法学习，落地为伪 AI（规则引擎）
- **仅数据好，无真实痛点** → 技术驱动而非业务驱动，成果无人使用
- **痛点+数据俱佳，但实施复杂** → 可以做，但应列为战略项目而非快赢项目
- **三维均衡且高分** → 最优突破口，应作为 Top 1 推荐

### 1.3 用户感知设计（简单化策略）

> **关键设计决策**：三个维度对用户**不直接展示维度名称**，而是转化为**3-5 个简单的情境化选择题**，后台算法根据答案自动映射到三个维度的分值。

**用户端呈现（示例）：**

```
针对"客户关系 CR"模块，请回答以下问题：

Q1【对应痛点迫切度】
"您的企业在客户关系管理上，最困扰您的是？"
○ A. 客户投诉多，处理速度跟不上（非常迫切）
○ B. 客户流失了才知道，缺乏预警（比较迫切）
○ C. 客户关系还可以，但感觉有提升空间（一般）
○ D. 客户关系管理目前没有明显问题（不迫切）

Q2【对应数据基础度】
"您目前的客户数据积累情况？"
○ A. 有完整的 CRM 系统，客户行为、消费记录完整（数据充足）
○ B. 有基础客户名单和购买记录，部分字段缺失（数据一般）
○ C. 主要靠销售人员的脑子和 Excel 表格（数据薄弱）
○ D. 基本没有系统化的客户数据积累（几乎无数据）

Q3【对应实施可行度】
"如果要在客户关系环节引入 AI 工具，您认为？"
○ A. 非常愿意尝试，团队有一定数字化基础（容易启动）
○ B. 愿意做，但需要一些培训和适应期（可以推进）
○ C. 有些顾虑，担心团队接受度和成本（有阻力）
○ D. 暂时不考虑，变革代价太大（阻力极大）
```

## 二、评分量表与后台权重算法

### 2.1 维度一：痛点迫切度（Pain Score）

**定义**：该画布要素对应的业务痛点，在当前阶段对企业经营的威胁程度与改善的紧迫性。

**评分量表（1-5分）：**

| 分值 | 档位名称 | 定义标准 | 用户选项映射 |
|-----|--------|--------|-----------|
| **5分** | 🔴 生死攸关 | 该问题已直接影响企业营收、客户流失或运营效率，不改变将导致持续失血。管理层已将其列为年度最高优先级。 | 选项A类（非常迫切） |
| **4分** | 🟠 显著痛点 | 问题明显存在，已有量化损耗（如可估算的人力浪费、客户流失率），管理层有共识需要改变，但尚未列为最高优先。 | 选项B类（比较迫切） |
| **3分** | 🟡 中度困扰 | 有明确的改善需求，但当前尚可维持运营。团队有感知但未量化损耗，属于"有机会改善"而非"必须立即改善"。 | 选项C类（一般） |
| **2分** | 🟢 轻度摩擦 | 偶发性问题或局部不满，整体运营不受影响。改善属于锦上添花而非雪中送炭。 | 选项D类（不迫切） |
| **1分** | ⚪ 无明显痛点 | 该要素运转良好，当前无改善动力。强行推进 AI 改造将面临组织阻力。 | 系统自动判定（若用户直接跳过该模块） |

---

### 2.2 维度二：数据基础度（Data Score）

**定义**：该画布要素对应业务环节的数据积累质量，直接决定 AI 模型能否被训练与落地。

**评分量表（1-5分）：**

| 分值 | 档位名称 | 定义标准 | 数据特征描述 |
|-----|--------|--------|-----------|
| **5分** | 💎 数据金矿 | 该环节拥有**海量、结构化、持续更新**的历史数据（如：系统化CRM记录≥2年、全量交易流水、完整操作日志）。AI 模型可直接基于现有数据训练，无需额外数据工程。 | 数据量级：百万条以上；结构化程度：≥80%；历史深度：≥2年 |
| **4分** | 🔵 数据充足 | 有较完整的业务数据记录，主要字段完备，但可能存在部分历史缺失或非结构化比例偏高（如：Excel管理但字段规范、部分系统化记录）。AI 落地需少量数据清洗工程。 | 数据量级：万级以上；结构化程度：50-80%；历史深度：1-2年 |
| **3分** | 🟡 数据基础 | 有基础数据记录，但分散在多个系统或个人手中（Excel、微信记录、人工台账），需要系统性的数据整合与清洗工作。AI 落地需先做数据治理。 | 数据量级：千级；结构化程度：30-50%；分散度高 |
| **2分** | 🟠 数据薄弱 | 数据主要以非结构化形式存在（纸质记录、人脑记忆、零散截图），或仅有极少量历史记录。AI 落地需先经历至少6个月的数据积累期。 | 数据量级：百级以下；非结构化为主；历史数据几乎缺失 |
| **1分** | 🔴 数据空白 | 该环节完全无数据积累，业务运行完全依赖个人经验与口头传授。AI 短期无法介入，需先完成业务数字化（上系统）才能谈AI。 | 无任何数字化记录；纯人工经验驱动 |

**【重要注释】数据基础度的特殊修正规则：**

> 当数据基础度 ≤ 2 分时，系统应在推荐结论中**自动附加"数据先行"预警标签**，说明该要素虽然可以作为突破方向，但需要在 AI 实施前完成数据基础设施建设，预计增加3-6个月的前期准备周期。

---

### 2.3 维度三：实施可行度（Feasibility Score）

**定义**：综合评估该要素在当前企业情境下启动 AI 改造的组织阻力、技术门槛与资源匹配度。

**评分量表（1-5分）：**

| 分值 | 档位名称 | 定义标准 | 综合判断要素 |
|-----|--------|--------|-----------|
| **5分** | 🚀 随时可启动 | 决策层支持明确；相关业务团队有数字化意愿；无重大系统集成障碍；有预算意愿；可在1-2个月内启动POC。 | 组织意愿强 + 技术门槛低 + 资源到位 |
| **4分** | ✅ 可推进 | 基本条件具备，但需要1-2个月的团队培训或小范围试点验证。主要障碍可在内部协调解决，无需重大组织变革。 | 条件基本具备，存在可克服的小阻力 |
| **3分** | ⚠️ 需要准备 | 有意愿但存在明显障碍：部分业务团队抵触、技术系统需要升级、或决策流程复杂。需要3-6个月的准备期。 | 中等阻力，需专项推进计划 |
| **2分** | 🔶 阻力较大 | 存在较大的组织或技术障碍（如：核心系统为遗留系统难以对接、关键部门负责人反对、预算受限），需要6个月以上的变革管理。 | 较大阻力，需高层专项推动 |
| **1分** | 🚫 当前不可行 | 存在根本性障碍（如：监管约束、核心系统完全封闭、决策层明确反对），当前阶段无法推进，建议列入12个月以后的规划。 | 根本性障碍，建议暂缓 |

### 2.4 后台计算公式（Backend Scoring Algorithm）

#### 基础公式：加权乘积混合模型

```
综合优先级得分（Priority Score）= 
    Pain Score × W₁  +  Data Score × W₂  +  Feasibility Score × W₃
    +  Pain Score × Data Score × 联动加成系数 α
```

#### 权重设置与理由

| 维度 | 权重 | 设置理由 |
|------|-----|--------|
| **痛点迫切度（Pain）W₁** | **0.40** | 痛点是 AI 项目存在的根本理由，也是获得组织支持的最重要依据；权重最高体现"业务驱动"而非"技术驱动"的方法论原则 |
| **数据基础度（Data）W₂** | **0.35** | 数据是 AI 落地的第一生产要素，决定技术方案的可行性边界；权重次高体现对 AI 落地现实条件的尊重 |
| **实施可行度（Feasibility）W₃** | **0.25** | 可行度决定项目能否真正落地，但相对前两者属于"执行层面"因素，权重最低；且可行度往往可以通过管理介入提升 |

**联动加成系数 α 的设计逻辑：**

```
联动加成 = Pain Score × Data Score × α（α = 0.05）

加成逻辑：当"业务痛点"与"数据基础"同时高分时，
说明该要素是AI改造的"黄金靶点"——
有真实痛点 + 有充足数据 = AI能解决真问题 + 技术上能做到
此时额外给予加分，放大"双高"情况下的推荐优先级。
```

#### 完整计算公式

```
Priority Score = 
    (Pain × 0.40) + (Data × 0.35) + (Feasibility × 0.25) 
    + (Pain × Data × 0.05)

理论最高分：
= (5 × 0.40) + (5 × 0.35) + (5 × 0.25) + (5 × 5 × 0.05)
= 2.00 + 1.75 + 1.25 + 1.25
= 6.25 分

理论最低分：
= (1 × 0.40) + (1 × 0.35) + (1 × 0.25) + (1 × 1 × 0.05)
= 0.40 + 0.35 + 0.25 + 0.05
= 1.05 分

实际得分区间：[1.05, 6.25]
```

#### 归一化处理（标准化至100分制，便于前端展示）

```
Normalized Score = (Priority Score - 1.05) / (6.25 - 1.05) × 100
                 = (Priority Score - 1.05) / 5.20 × 100

即：
  最高分 6.25 → 归一化 100分
  最低分 1.05 → 归一化   0分
  中位分 3.65 → 归一化 ~50分
```

#### 附加规则：一票否决条件（Hard Constraint Rules）

> 以下任一条件成立时，无论综合得分多高，该要素**不得**作为 Top 突破要素推荐，系统应自动标注"⚠️暂缓"并说明原因：

```yaml
hard_block_rules:
  rule_1:
    condition: "Feasibility Score == 1"
    reason: "存在根本性实施障碍，强行推进将浪费资源并损伤团队信心"
    output_label: "🚫 当前不可行·建议12个月后重新评估"
    
  rule_2:
    condition: "Data Score == 1 AND Pain Score <= 3"
    reason: "数据空白且痛点不算严重，AI投入产出比极低"
    output_label: "⚠️ 数据先行·建议先完成数字化基础建设"
    
  rule_3:
    condition: "Pain Score <= 2"
    reason: "痛点不明显，强行引入AI缺乏组织动力，项目极易烂尾"
    output_label: "💡 暂不推荐·当前阶段优先聚焦更迫切的要素"
```

## 三、优先级矩阵映射

### 3.1 四象限矩阵定义

> **矩阵坐标系设计**：
> - X轴：数据基础度（Data Score），代表"技术实现难度"（从左到右：困难→容易）
> - Y轴：痛点迫切度（Pain Score），代表"业务价值高低"（从下到上：低→高）
> - 气泡大小：实施可行度（Feasibility Score），气泡越大代表越容易推进

```
           高痛点（Pain ≥ 4）
                ▲
                │
  ┌─────────────┼─────────────┐
  │             │             │
  │  ② 战略攻坚区  │  ① 快赢黄金区  │
  │  Pain高,Data低  │  Pain高,Data高  │
  │  "先建基础,后上AI"│  "立即启动,优先突破"│
  │             │             │
  │             │             │
◄─┼─────────────┼─────────────┼─►
Data低          │          Data高
（≤2分）         │          （≥4分）
  │             │             │
  │  ④ 暂缓观望区  │  ③ 长效培育区  │
  │  Pain低,Data低  │  Pain低,Data高  │
  │  "当前不是时机"  │  "数据已就绪,等待痛点" │
  │             │             │
  │             │             │
  └─────────────┼─────────────┘
                │
           低痛点（Pain ≤ 2）
```

### 3.2 四象限详细定义与处理策略

#### ① 快赢黄金区（Quick Win Zone）
```yaml
条件:
  Pain Score: ≥ 4
  Data Score: ≥ 4
  Feasibility Score: 任意（但须 ≥ 2）
  
归一化总分区间: ≥ 70分

定义: >
  业务痛点明确且紧迫，数据基础充分，
  AI改造的投入产出比最高，是最优先的突破口。
  可在90天内完成POC并看到明显效果，
  是建立组织对AI信心的理想起点。

系统处理:
  推荐等级: ⭐⭐⭐ Top推荐
  是否自动列入Top 3: 是（得分最高的3个）
  前端标签: "🚀 强烈推荐·快速见效"
  建议行动时间: 立即启动（30天内）
```

#### ② 战略攻坚区（Strategic Zone）
```yaml
条件:
  Pain Score: ≥ 4
  Data Score: ≤ 3
  Feasibility Score: 任意

归一化总分区间: 50-70分

定义: >
  痛点真实且重要，但数据基础不足制约了AI的直接落地。
  这类要素具有高战略价值，但需要先期投入数据基础建设。
  适合列为"12-24个月战略项目"，先上系统积累数据，
  再推AI改造。

系统处理:
  推荐等级: ⭐⭐ 战略推荐
  是否自动列入Top 3: 视情况（若快赢区数量 < 3个，补位）
  前端标签: "📋 战略布局·先建数据基础"
  系统自动附加提示: 
    "该要素痛点明确，但建议先完成以下数据基础建设：[具体建议]，
     预计[X]个月后可启动AI改造"
  建议行动时间: 3-6个月内启动数据基础建设
```

#### ③ 长效培育区（Long-term Zone）
```yaml
条件:
  Pain Score: ≤ 3
  Data Score: ≥ 4
  Feasibility Score: 任意

归一化总分区间: 40-60分

定义: >
  数据基础良好，但当前业务痛点不够明显，
  组织的改变动力不足。
  这类要素适合"润物无声"地推进——
  利用已有数据资产做低成本的AI探索，
  待痛点浮现时能快速规模化。

系统处理:
  推荐等级: ⭐ 培育推荐
  是否自动列入Top 3: 否（作为备选提示）
  前端标签: "🌱 培育机会·数据已就绪"
  建议行动时间: 可在其他项目推进中并行低投入探索
```

#### ④ 暂缓观望区（Hold Zone）
```yaml
条件:
  Pain Score: ≤ 3
  Data Score: ≤ 3
  或满足任一一票否决规则

归一化总分区间: < 40分

定义: >
  当前时机不成熟：痛点不明显或数据基础薄弱，
  此时推进AI改造性价比极低，容易产生"为了AI而AI"的
  形式主义项目，浪费资源并消耗组织信心。

系统处理:
  推荐等级: 不推荐
  是否自动列入Top 3: 否
  前端标签: "⏸ 暂缓·当前条件不成熟"
  建议行动时间: 12个月后重新评估
```

### 3.3 Top 3 突破要素自动遴选规则

```
Step 1：对所有9个画布要素按归一化总分排序（从高到低）

Step 2：从高分到低分依次入选，但须满足：
  ① 不触发任何一票否决条件
  ② 优先选满足"快赢黄金区"条件的要素
  ③ 若快赢区数量 < 3个，则从"战略攻坚区"补位

Step 3：最终确保 Top 3 要素之间的"互补性"检验：
  若3个要素均集中在同一画布方向（如均为内部效率类：KA/KR/C$），
  系统应提示建议：
  "您当前选择的突破要素集中在内部效率优化，
   建议考虑增加一个市场侧要素（CS/VP/CH/CR），
   以形成'内外兼修'的创新组合。"

Step 4：学员可在系统推荐基础上手动调整，
  但若选择得分低于40分的要素，系统弹出确认提示。
```

### 3.4 分数段与标签速查表

### 4.2 系统问卷收集与原始分值映射

**Q1：痛点迫切度评估**

```
问题: "您的企业在客户关系管理上，最困扰您的是？"

学员选择: B（"客户流失了才知道，缺乏预警"）

系统映射: Pain Score = 4分

【评分注释】：
学员描述中出现"老客户突然不下单"、"事先完全不知道"、
"销售离职带走客户"等关键词，系统通过NLP语义识别，
将痛点严重程度上调至 4.5 分（语义增强分）。

Pain Score（最终）= 4.5 分 ✓
```

**Q2：数据基础度评估**

```
问题: "您目前的客户数据积累情况？"

学员选择: C（"主要靠销售人员的脑子和Excel表格"）

【评分注释】：
学员描述提及"客户资料在销售手机通讯录"（= 非结构化、个人持有），
"想做CRM但不知从哪入手"（= 尚未上系统），
语义识别确认数据基础薄弱，维持 Data Score = 2分。

Data Score（最终）= 2 分 ✓
```

**Q3：实施可行度评估**

```
问题: "如果要在客户关系环节引入AI工具，您认为？"

学员选择: B（"愿意做，但需要一些培训和适应期"）

系统映射: Feasibility Score = 4分

【评分注释】：
学员主动表达"想做CRM"的意愿，且企业规模（200客户）
适中，CRM工具导入难度可控。但存在"销售人员抵触
（担心客户资产被公司拿走）"的潜在阻力，略微下调至 3.5 分。

Feasibility Score（最终）= 3.5 分 ✓
```

### 4.3 后台计算过程（完整演示）

```
Step 1：代入计算公式

Priority Score（CR）
= (Pain × 0.40) + (Data × 0.35) + (Feasibility × 0.25) 
  + (Pain × Data × 0.05)

= (4.5 × 0.40) + (2.0 × 0.35) + (3.5 × 0.25) 
  + (4.5 × 2.0 × 0.05)

= 1.800 + 0.700 + 0.875 + 0.450

= 3.825 分（原始分）
```

```
Step 2：归一化处理

Normalized Score（CR）
= (3.825 - 1.05) / 5.20 × 100
= 2.775 / 5.20 × 100
= 53.4 分
```

```
Step 3：一票否决规则检验

✅ Rule 1 检验：Feasibility Score = 3.5 ≠ 1  → 通过
✅ Rule 2 检验：Data Score = 2，Pain Score = 4.5 > 3  → 通过
✅ Rule 3 检验：Pain Score = 4.5 > 2  → 通过

→ 无否决规则触发，CR 进入正常推荐流程 ✓
```

```
Step 4：象限归属判断

Pain Score = 4.5 ≥ 4  → Y轴：高痛点区域 ✓
Data Score = 2.0 ≤ 3   → X轴：低数据区域 ✓

→ 归属象限：② 战略攻坚区 ✓

Normalized Score = 53.4分 → 对应"战略攻坚区"分段（50-60分） ✓
```

```
Step 5：推荐等级确定

象限：战略攻坚区
推荐等级：⭐⭐ 战略推荐
前端标签："📋 战略布局·先建数据基础"
```
